# MS-ODRAW geometry notes: freeform paths, preset shapes, WordArt

Written by the docs lane (docs only) on 2026-10-23 from the PUBLIC Microsoft specification [MS-ODRAW] (Office Drawing Binary File Format), read on Microsoft Learn. This is an allowed input under docs/PUB-AGENTS.md section 2. The text below is a paraphrase in our own words; nothing was copied from any .pub reader, and no web search for .pub format details was done. Every statement is marked SPEC (stated by MS-ODRAW, section cited), INFERENCE (our reasoning) or UNKNOWN (settle it from data files).

## 1. Freeform paths (unblocks ROADMAP C7)

SPEC (2.3.6.1-2.3.6.4): geoLeft (property id 0x0140), geoTop (0x0141), geoRight (0x0142), geoBottom (0x0143) set the shape geometry space. Defaults: 0, 0, 0x5460 (21600), 0x5460.
SPEC (2.3.6.5, 2.4.9): shapePath (0x0144) says how vertices are joined: 0 Lines (open straight), 1 LinesClosed (the default), 2 Curves (open Bezier), 3 CurvesClosed, 4 Complex. With Complex the pSegmentInfo_complex data must exist. If pSegmentInfo_complex is present and non-empty, shapePath is ignored and the segment records decide.
SPEC (2.3.6.6-2.3.6.7): pVertices (0x0145) is the property header; when its complex flag is set the data lives in pVertices_complex, an IMsoArray of POINT values. POINT (2.2.55) is two signed 4-byte integers, x then y. Coordinates are geometry-space units, except values in 0x80000000..0x8000007F, which are not coordinates but indexes into the pGuides_complex array (2.3.6.27); the spec text writes the subtraction constant as 0x8000000, which looks like a typo for 0x80000000. UNKNOWN: confirm the index base from data; neither C7 sample contains guide references (see §5).
SPEC (2.3.6.8-2.3.6.9): pSegmentInfo (0x0146) is the header; pSegmentInfo_complex is an IMsoArray of MSOPATHINFO records (2.2.53), 16 bits each, that say how to walk the vertex list.
SPEC (2.2.51): an IMsoArray starts with three 2-byte fields: nElems (count), nElemsAlloc (capacity, at least nElems), cbElem (bytes per element). When cbElem is 0xFFF0 the elements are truncated 8-byte values stored as 4 bytes each (high 4 bytes are zero). Data size is nElems times cbElem, or nElems times 4 when cbElem is 0xFFF0.
UNKNOWN: how a 4-byte element is split into x and y when cbElem is not 8 (for example two 16-bit values). Both shapes__curve and shapes__polyline contain only eight-byte vertices, so they do not settle this question (see §5); do not guess.

### Path record (MSOPATHINFO, 2.2.53) and path types (2.4.30)
SPEC: a record holds a 3-bit type and a 13-bit segment count. If the type is the escape value, the record is read as MSOPATHESCAPEINFO (2.2.54): 3-bit type, 5-bit escape code, 8-bit segment count. OBSERVATION: both C7 fixtures put the type in the high three bits, and the count in the low 13; see the words and vertex-count check in §5.
SPEC path types: 0 LineTo (one point per segment, straight line from the current end), 1 CurveTo (three points per segment: two control points then the end point, a cubic Bezier), 2 MoveTo (starts a sub-path with one point; segment count must be 0), 3 Close (draws a straight line back to the start if needed; segment count must be 1; uses no points), 4 End (end of the path), 5 Escape (read the escape record), 6 ClientEscape.
SPEC escape codes (2.4.31, values read so far): 0x00 Extension (adds points to the escape that follows), 0x01 AngleEllipseTo, 0x02 AngleEllipse, 0x03 ArcTo, 0x04 Arc, 0x05 ClockwiseArcTo, 0x06 ClockwiseArc, 0x07 EllipticalQuadrantX, 0x08 EllipticalQuadrantY, 0x09 QuadraticBezier, 0x0A NoFill, 0x0B NoLine, 0x0C AutoLine, 0x0D AutoCurve, 0x0E CornerLine, 0x0F CornerCurve, 0x10 SmoothLine, 0x11 SmoothCurve, 0x12 SymmetricLine, 0x13 SymmetricCurve, 0x14 Freeform. More values follow (fill and line colour escapes); they were not read yet. For AngleEllipseTo/AngleEllipse the spec says: first point is the centre, second point holds the x radius and y radius, third point holds the start angle and end angle in degrees; the number of ellipse segments is the segment count divided by three.
INFERENCE (not stated in one place): to draw, scale geometry space [geoLeft..geoRight] x [geoTop..geoBottom] onto the shape frame, then follow the segment records in order. A first importer can safely handle MoveTo, LineTo, CurveTo, Close and End, and keep a warning for every escape code it does not implement.

## 2. Preset shapes (relates to ROADMAP C8)

SPEC (2.4.24 MSOSPT): the enumeration gives the preset shape numbers and a one-line English description only, for example 74 (0x4A) Heart is described as a heart shape, 1 Rectangle, 2 RoundRectangle, 19 Arc, 95 BlockArc. 203 names were counted.
OBSERVATION about the spec: MS-ODRAW does NOT define the vertices or guide formulas for preset shapes. So heart (74) and the other presets cannot be drawn from MS-ODRAW alone. UNKNOWN: whether Publisher stores explicit vertices for a preset in the file (check the heart fixture for pVertices data) or relies on built-in geometry.
DECISION NEEDED FROM THE OWNER (PUB-AGENTS.md section 2): the public ECMA-376 preset shape definitions (OOXML presetShapeDefinitions) define heart and the text-warp geometries. It is not a .pub reader, but it is not on the allowed list. Use it only if the owner writes: the owner approves ECMA-376 preset shape definitions as an input for C8 and C9.

## 3. WordArt (relates to ROADMAP C9)

SPEC (2.4.24): WordArt uses preset text shape types. Values read: 24 TextSimple, 25 TextOctagon, 26 TextHexagon, 27 TextCurve, 28 TextWave, 29 TextRing, 30 TextOnCurve, 31 TextOnRing, 136 TextPlainText, 137 TextStop, 138 TextTriangle, 139 TextTriangleInverted, 140 TextChevron, 141 TextChevronInverted, 142 TextRingInside, 143 TextRingOutside, 144 TextArchUpCurve, 145 TextArchDownCurve, 146 TextCircleCurve, 147 TextButtonCurve, 148 TextArchUpPour, 149 TextArchDownPour, 150 TextCirclePour, 151 TextButtonPour, 152 TextCurveUp, 153 TextCurveDown, 154 TextCascadeUp, 155 TextCascadeDown, 156-159 TextWave1-4, 160 TextInflate, 161 TextDeflate, 162 TextInflateBottom, 163 TextDeflateBottom, 164 TextInflateTop, 165 TextDeflateTop, 166 TextDeflateInflate, 167 TextDeflateInflateDeflate, 168-171 TextFadeRight/Left/Up/Down, 172 TextSlantUp, 173 TextSlantDown, 174 TextCanUp, 175 TextCanDown. (Value 202 is a plain text box, not WordArt.)
SPEC geometry-text properties (2.3.22): gtextUNICODE 0x00C0 (the text; string in the complex part), gtextAlign 0x00C2 (default centre), gtextSize 0x00C3 (default 0x00240000), gtextSpacing 0x00C4 (default 0x00010000), gtextFont 0x00C5 (font name, complex part; default empty), gtextCSSFont 0x00C6, and a boolean group 0x00FF whose flags include fGtext (WordArt on), vertical, kern, tight, stretch, shrink-to-fit, best fit, normalize, bold, italic, underline, shadow, small caps, strikethrough and reverse rows. INFERENCE: 0x00240000 read as 16.16 fixed point is 36 points and 0x00010000 is 1.0; confirm on data.
SPEC (2.3.6.31): the geometry boolean group 0x017F has an fGtextOK flag.
OBSERVATION about the spec: the text-warp shapes are named but their warp geometry (how an arch or circle bends the letters) is not defined. Until the owner approves an extra source, the importer can read the text, font, size and WordArt flag, and keep a warning that the warp is not applied (as it does today).

## 4. What this settles for the code queue
- C7 freeform curves: §5 settles the path-type bits and records the observed eight-byte vertices. Move, line, cubic, close and end can be imported with warnings for unsupported escapes. Four-byte vertices and guide indexes remain UNKNOWN and unsupported. Do not edit protected readers except as the task allows.
- C8 preset shapes: can recognise type numbers, cannot draw them. Stays BLOCKED for geometry unless the fixtures store vertices or the owner approves ECMA-376.
- C9 WordArt: can read the text properties; warp geometry stays BLOCKED on the same decision.
- Section numbers above are MS-ODRAW sections; the property ids and default values were read from their pages on 2026-10-23.

## 5. OBSERVATION — C7 sample paths, 2026-10-24

Only the .pub data in `shapes__curve.pub` and `shapes__polyline.pub` at pubsmith commit `0ccdf27fc3f381f0897515e226ea485165c699b2` was used for these observations. Read the Escher stream with this project's existing `escher::parse`; no scoring exports were used to document how the file stores the path from the sample files.

OBSERVATION (`shapes__curve.pub`): shape type 0, Contents sequence 293; pVertices has array header `(4, 4, 8)`, followed by four signed 32-bit x/y pairs: `(0, 1625600)`, `(990600, 0)`, `(2260600, 3251200)`, `(3530600, 1625600)`. Geometry right/bottom are `3530601 / 3251201`, left/top absent (default 0). pSegmentInfo has header `(5, 5, 2)` and little-endian words `4000 AD00 2001 AD00 8000`.

OBSERVATION (`shapes__polyline.pub`): same type and sequence; pVertices has header `(4, 4, 8)` and pairs `(0, 0)`, `(1828800, 0)`, `(1828800, 1828800)`, `(0, 0)`. Geometry right/bottom are both `1828801`. Segment header `(6, 6, 2)`; words `4000 AC00 0003 AC00 6001 8000`.

OBSERVATION (both files): the type occupies the high three bits (`word >> 13`), with the remaining low 13 bits holding the count. This gives MoveTo/0, CurveTo/1 or LineTo/3, Close/1 in the polyline, and End; each walk consumes exactly the four vertices. Using the low three bits as type instead would start `4000` as LineTo/2048, incompatible with four available vertices. The intervening `AD00` and `AC00` records have escape type 5, codes 0x0D and 0x0C, and low-byte count 0, using the documented escape layout. Their effects are not implemented; preserve a warning rather than silently treating them as drawing commands.

UNKNOWN (four-byte vertex split): neither sample has cbElem 4 or 0xFFF0; both use 8. These files cannot settle how a four-byte element divides into x and y, or its signedness. Stop that part: keep a warning and rectangle fallback for these vertex element sizes. Needed: a controlled path file containing four-byte vertices with independently distinguishable x/y values.

UNKNOWN (guide index base): neither sample has a coordinate in 0x80000000..0x8000007F. They cannot settle the base, guide evaluation or references. Stop that part: detect these references and keep a warning and rectangle fallback. Needed: controlled paths with guide references and enough independently known guide values to distinguish the index base. Do not evaluate or reinterpret guides by guessing.

INFERENCE (bounded implementation): for the observed eight-byte vertices, map x/y from documented geometry bounds to the frame and walk MoveTo, LineTo, CurveTo, Close and End. Zero-point escape records can be skipped with a warning without losing the vertex cursor; their visual effects remain unimplemented. For an unsupported record that may consume points, stop the walk, keep any drawable prefix and warn; do not guess how to resume. Validate array sizes/capacity, point counts, finite scales, required move/close counts and a current subpath before drawing. End stops the walk. Invalid paths fall back with a warning rather than crashing.
