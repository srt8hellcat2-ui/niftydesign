# Roadmap: Publisher parity for every .pub file

Written 2026-11-22. This is the plan for opening, showing, editing and exporting every kind of `.pub` file the way Microsoft Publisher does. It builds on [pub-import-status.md](../pub-import-status.md), [publisher-parity-checklist.md](../publisher-parity-checklist.md), [legacy-minimal-reader.md](legacy-minimal-reader.md) and the clean-room rules in [PUB-AGENTS.md](../PUB-AGENTS.md).

## 1. What "100% parity" can mean

Parity cannot be declared by reading files alone. The project has never compared a result with what Publisher draws for the same file (task 5.2), and the clean-room rules forbid reading how any other program behaves. So the roadmap uses five levels. A file is only called "at parity" when it reaches level 4.

| Level | Meaning | How it is checked |
|---|---|---|
| 0 Opens | The file opens, the text is readable, nothing crashes. | Batch conversion of the whole corpus. |
| 1 Complete content | Every story, picture and object that is in the file is in the result. | Counts against the stored structure; nothing silently dropped. |
| 2 Right place | Pages, sizes and object positions match the file. | Positions against stored numbers and the stored page preview. |
| 3 Right look | Fonts, colours, fills, lines, tables, WordArt and pictures look as stored. | Side by side with a **Publisher-made reference render** supplied by the owner. |
| 4 Parity | Levels 0 to 3 hold for the file, and a person has compared it with Publisher. | The owner's review of the reference comparison. |

What is never in scope: writing `.pub` files, mail merge, the design checker, templates, Pack and Go ([checklist, out of scope](../publisher-parity-checklist.md)).

## 3. Workstreams

Order inside a workstream is the order to do things. "Needs" says what must exist first.

### W0. Measure parity before claiming it (do this first)

Without it every other item is a guess.

| # | Milestone | Needs | Done when |
|---|---|---|---|
| 0.1 | Reference renders: for a chosen set of files, the owner saves a PDF or page image from Publisher itself. They are data used only for scoring, never to learn encodings (PUB-AGENTS section 2). | The owner's Publisher and files | At least 40 files across all generations, listed with hashes. |
| 0.2 | Comparison harness: render our result and the reference at the same size, report a pixel difference per page and keep side-by-side images. Extends [pixel-diff.md](pixel-diff.md). | 0.1 | One command prints per-file level-3 results; thresholds written down. |
| 0.3 | Level table in the status doc, per file, regenerated by the command. | 0.2 | `pub-import-status.md` shows levels, not only "opens". |
| 0.4 | Desktop check: open, edit, save and print on a real Windows desktop. | A person at the machine | The three UNVERIFIED rows of the checklist are closed. |

### W2. Legacy files, Publisher 2.0 to 2000 (families A, B, C, D)

These files have no public specification. Everything here comes from observing the owner's data files and must stay labelled OBSERVATION, INFERENCE or UNKNOWN.

| # | Milestone | Needs | Done when |
|---|---|---|---|
| 2.1 | Page size verification: compare the root pair with the preview aspect and with files of known size. The pairs match Letter and A4 in EMU, so the unit is already strongly supported. | Donated files with known sizes | The size warning goes away for verified sizes; implausible values keep the fallback. |
| 2.2 | Pages: page records, order and master pages for A/B (order by directory is done); C and D have none yet. | More C files with several pages | Page count equals the preview or the owner's count on every file. |
| 2.3 | Frame positions for C files. The rectangle layout used by A/B does not fit C (half-root containment fails in 58 linked records). | Study of the C record types | C files place text at stored positions. |
| 2.4 | D layout: the layout table of the 0x00c8 files differs and, in two files, starts after an embedded printer name. | The eight donated files and more | Positions and page size for D files, or a note saying why not. |
| 2.5 | Colours. Frame fill literals are done. The small scheme numbers index a colour scheme; some files store the scheme's colours, but built-in schemes (Bluebird, Dark Blue and others) store none. | The built-in scheme tables, which are **not** in the files | Either the owner supplies the scheme colours as data, or built-in schemes stay unresolved with a clear note. |
| 2.6 | Shapes and lines: object kinds (layout indices 2 to 7, 15, 40), line colour and weight, per-side borders, rotation, shadows. | 2.5 for most colours | Rectangles, ovals, lines and bars are drawn and compared with the preview. |
| 2.7 | Pictures: cropping, rotation, borders, metafile pictures that are drawings, `OlePres` previews with no index-33 picture. | More picture files | Every stored picture is placed. |

### W5. A familiar workspace (optional, separate from file parity)

A switch for people who know Publisher's layout: **Window > Workspace > Publisher-style**, remembered per user, with the native layout one click away. Everything in the app is already a command, and menus, shortcuts and panel docking are data in `crates/ui-egui`, so this is a preset, not a second UI.

| # | Milestone | Done when |
|---|---|---|
| 5.1 | Menu preset: the same commands grouped under the headings a Publisher user expects (File, Edit, View, Insert, Format, Tools, Table, Arrange, Window, Help). | Every command is reachable in both layouts; none is lost. |
| 5.2 | Shortcut preset: a second key map, switchable, with conflicts reported. | The map is data; a test checks every key is bound once. |
| 5.3 | Panel preset: object toolbar on the left, formatting toolbar on top, task-style panel on the right. | The preset restores on restart. |
| 5.4 | Wording preset: Publisher's terms for the same things (text box, master page, and so on) as labels only. | Labels change; command ids do not. |

Limits: use feature names and plain functional descriptions only. No Microsoft icons, artwork or text, and no "Publisher" product branding on the toggle, with the same non-affiliation line the README uses. Observing Publisher's own interface for the layout is not covered by the format rules in PUB-AGENTS and needs the owner's say-so, like the reference renders in 0.1.

## 4. Suggested order

1. **W0.1 to W0.3**: nothing after this can be proven without it.
2. **W3.1, W3.3, W3.4** (the 2002+ gaps with the highest weight) together with **W2.1 and W2.2** (legacy pages and sizes).
3. **W2.3 and W2.4** (C and D positions), then **W2.5 to W2.9** as colour and sample data arrive.
4. **W1.1** when five more flat files exist.
5. **W3.5 to W3.11** and the rest of **W2**, by checklist weight.
6. **W0.4** whenever a person is at a Windows desktop.
7. **W5** (the Publisher-style workspace) once file parity work is under way; it does not depend on it.

| Need | Unlocks |

## 6. Honest limits

- Where the real program draws something that depends on its own built-in tables (colour schemes, fonts, layout rules), a file alone may never be enough. Those items end as "resolved with data from the owner" or "stays an approximation, documented".
- Percentages in the checklist are an upper bound (it says so itself). This roadmap adds levels so a number can only rise when someone compared a result with Publisher.
- The text-only profile D and the inferred Windows-1252 decoding are working choices made on 2026-11-22 from observation, labelled as such in the notes and in every report. They can be reversed in one place each (`crates/pub-legacy/src/early.rs` and `codepage.rs`).
